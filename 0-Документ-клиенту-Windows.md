Пошаговая инструкция для миграции Windows-ВМ из VMware в KVM (MWS Cloud Platform)

---

## Требования

- Windows Server 2019 или новее.
- Права администратора на ВМ.
- 2 ГБ свободно на `C:`.
- Интернет или установщики в `windows\tools\`.

Не поддерживается: Windows Server 2016/2012 (нет `mbr2gpt.exe`), Windows 7/8/8.1. Для них – In-Place Upgrade или чистая установка в KVM.

---

## Структура пакета

```
windows\
├── 1-run.bat                  ← точка входа
├── 2-Orchestrator.ps1         ← определяет состояние, запускает нужное
├── 3-Diagnostic.ps1           ← диагностика (read-only)
├── 4-Migration.ps1            ← трансформация
├── 5-Post-Migration.ps1       ← чистка VMware-мусора (запуск в KVM)
├── 6-CloudBase-Init.ps1       ← опционально: metadata
├── 7-Sysprep.ps1              ← опционально: golden image
├── configs-cloudbase-init\
├── tools\                     ← положите установщики сюда
└── logs\                      ← создаётся при запуске
```

---

## Что делает toolkit

На исходной Windows-ВМ:

- Проверяет совместимость.
- Конвертирует MBR в GPT для загрузки в режиме UEFI.
- Устанавливает драйверы VirtIO.
- Регистрирует `vioscsi` как boot-critical.
- Создаёт devnode в `Enum\PCI`. Без него Windows не загрузится в KVM.
- Пересобирает UEFI BCD, добавляет fallback-загрузчик.
- Сбрасывает сеть на DHCP, включает RDP и ICMP, отключает NLA.
- Выключает ВМ для экспорта.

Что не делает: не меняет данные, не переустанавливает приложения, не обновляет ОС, не решает лицензионные вопросы.

## Порядок работы

### Этап 1. На исходной ВМ (VMware)

1. Скопируйте папку `migration-to-mws\windows\` на рабочий стол ВМ.
2. Убедитесь, что в `tools\` лежат `virtio-win-guest-tools.exe` и `CloudbaseInitSetup_x64.msi`. Если их нет – скрипты скачают из интернета.
3. Запустите `1-run.bat` правой кнопкой → «Запуск от имени администратора».
4. Дождитесь выключения ВМ. Перед выключением, в консоли будет пауза `Press Enter to Shutdown` – чтобы можно забрать логи из `logs\`.

Опционально, можете изучить шаги и статус подготовки ВМ в логе `4-Migration_*.log`:

```
PREPARATION COMPLETED SUCCESSFULLY
STEP 3.5b: VERIFIED: devnode has Service=vioscsi
```

Если строки есть – переходите к этапу 2. Если `CRITICAL ERROR` – приложите лог в поддержку.

### Этап 2. Экспорт и передача в MWS

ВМ выключена. Экспортируйте её штатным способом (своими руками или через поддержку вашего облака), загрузите диск в S3 бакет MWS Cloud Platform и сгенерируйте\получите Path-Style PreSigned URL для импорта в Compute.

### Этап 3. Импорт в MWS

1. Compute → Образы → Создать → Образ по ссылке. Вставьте PreSigned URL, укажите тип ОС = Windows и необходимый размер образа диска > 40 ГБ.
2. Compute → ВМ → Создать из имеющегося образа. Задайте vCPU, RAM, зону размещения.
3. Настройте сеть: подсеть, внешний IP (`oneToOneNat`), 
4. После создания и запуска ВМ, откройте правило файрвола для RDP (3389) на доступ только для своего адреса. Узнать свой внешний IP: https://ifconfig.me
5. Подключитесь по RDP с вашим старым логином и паролем из исходной ВМ. Первый boot занимает 5 минут.

### Этап 4. Пост-настройка (опционально)

Внутри работающей ВМ в KVM:

- `5-Post-Migration.ps1` – удаление VMware Tools, phantom-устройств, мёртвых служб.
- `6-CloudBase-Init.ps1` – установка CloudBase-Init для управления паролем (установка нового пароля, сброс забытого) через metadata MWS.
- `7-Sysprep.ps1` – подготовка golden image. Необратимо.

## Где смотреть логи

```
windows\logs\3-Diagnostic_*.log
windows\logs\4-Migration_*.log
windows\logs\5-Post-Migration_*.log
```

Логи полезны для поддержки или самостоятельного анализа причин завершения работы скрипта. В конце каждого лога – итоговая сводка: что выполнено, что пропущено, что пошло не так.

## Если что-то пошло не так

**Скрипт упал с «mbr2gpt.exe NOT FOUND»**
Windows 2016 или старше. Обновите ОС или разверните чистую ВМ в KVM.

**Windows не грузится в KVM, ошибка 0xc0000001**
Проверьте в `4-Migration_*.log` строку `STEP 3.5b: VERIFIED: devnode has Service=vioscsi`. Если строки нет – devnode не создался, приложите лог в поддержку. Если строка есть – смотрите конфигурацию ВМ в MWS: machine type, firmware, дисковый контроллер.

**VMware Tools остался после миграции**
Перезагрузите ВМ, запустите `5-Post-Migration.ps1` повторно.

**RDP не подключается**
Проверьте правило файрвола для порта 3389 – оно должно быть открыто для вашего IP. Для базовой диагностики используйте Серийную консоль в панели MWS.

**Пароль администратора не работает после миграции**
Если вы не запускали `6-CloudBase-Init.ps1` – пароль остался старый из VMware. Смените вручную через Серийную консоль, либо выполните 5 → 6 → 7 и пересоздайте ВМ из образа.

**Можно ли запускать скрипты повторно?**
Да, они идемпотентны. На уже GPT-диске `4-Migration.ps1` пропустит конвертацию и выполнит только недостающие шаги.

**Как понять, что миграция прошла успешно?**
ВМ загружается в KVM, RDP работает, в Device Manager диск виден как MWS PersistentDisk. Скрипт `5-Post-Migration.ps1` завершается без оставшихся проблем.

**Какого типа должна быть ссылка на образ?**
Только Path-Style PreSigned URL, вида `https://storage.mwsapis.ru/xxx/disk.vmdk?X-Amz-...`. Virtual-Hosted-Style не принимается.
